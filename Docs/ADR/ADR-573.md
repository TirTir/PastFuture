# ADR-573 Entity ID와 GameObject 연결 등록부 (M1)

- Status: Validated
- SourceStep: 17 / M1 3단계 (2026-11-26, 사용자 승인 "3단계 진행")
- Related: ADR-008, ADR-018, ADR-493, ADR-494(모두 제목 또는 요약 제목만), ADR-569, ADR-572 / Handover 4절 M1, 16-2, 16-15, 16-17 / UNITY_T023, UNITY_T024

## Context
- **M1 범위 (Handover 4절):** "Entity binding"이 들어 있고, 완료 기준은 "ID와 GameObject 정합성"이다.
- **16-2:**
  - 모든 실체는 안정적인 ID를 쓴다.
  - 고정 인물·시설은 콘텐츠에서 정한 EntityId를 쓰고, 동적 개체는 Loop별 할당기가 고유 ID를 준다.
  - 과거 참조는 `(SessionId, LoopId, EntityId)`로 한다.
- **16-17:**
  - `EntityBindingContext`는 Session/Loop/Entity/Definition/ExecutionGeneration/BindingGeneration/Asset/Region으로 이루어진다.
  - 실제 Entity를 조회한 뒤 Prefab을 확보하고 상태를 적용한다.
  - 실제 interaction·physics 권한이 중복되면 안 된다.
  - 이전 Binding의 콜백은 거부한다.
  - Unload, OnDestroy, Pool 반환은 실제 사망이 아니다.
  - `IEntityPresentationRegistry`가 후보 인터페이스로 적혀 있다.
- **테스트 ID**
  - UNITY_T024: 중복 Entity binding → 권한 차단.
  - UNITY_T023: 이전 Scene 콜백 → generation 차단.
- **원문 한계**
  - ADR-008(안정적인 Entity ID)과 ADR-018(고정/동적 Entity ID 범위)은 요약 제목만 남아 있다.
  - ADR-493(Entity Presentation Registry)과 ADR-494(BindingGeneration 기반 표현 격리)는 제목만 남아 있다.
  - ID 형식과 범위 수치는 원문에 없다.
- **아직 없는 것:** WorldState, IdAllocator, Session/Loop는 M2 범위다.

## Decision
- **Domain `EntityId`** (`PastFuture.Domain.Entities`)
  - 양수 `long`을 감싼 readonly struct다. `None`(0)은 "개체 없음"을 뜻한다.
  - 고정/동적 범위 구분과 `LoopEntityRef`는 M2 IdAllocator에서 정한다.
- **Application**: `PastFuture.Application.Entities`, 엔진 무관
  - `IEntityPresentation`: 표현 쪽 객체의 최소 계약(`EntityId`, `DebugName`).
  - `EntityBinding`: 16-17 `EntityBindingContext`의 부분집합으로, `EntityId`와 `BindingGeneration`만 담는다. 나머지 필드는 해당 개념이 생길 때 추가한다.
  - `IEntityPresentationRegistry` / `EntityPresentationRegistry`
    - Entity와 표현 객체를 양방향으로 조회한다.
    - 이미 바인딩된 Entity에 두 번째 표현이 오면 `RejectedDuplicateEntity`로 거부하고, 처음 것이 권한을 유지한다.
    - 같은 표현 객체를 다시 바인딩하면 거부한다.
    - `BindingGeneration`은 바인딩마다 새로 증가하는 값이다.
    - `IsCurrent`와 `Unbind`는 generation이 현재 값과 같을 때만 통과한다. 그래서 이전 token으로 들어온 늦은 콜백은 아무것도 바꾸지 못한다.
    - `UnbindAll`은 모든 token을 무효로 만든다. generation은 계속 증가한다.
    - 표현 객체는 참조 동일성으로 비교한다. Unity 객체의 `==` 재정의를 쓰지 않기 위해서다.
    - main thread 전용이다. WorldState가 아니며 Entity의 상태를 결정하지 않는다.
- **UnityAdapters**: `PastFuture.UnityAdapters.Entities`
  - `EntityView`(MonoBehaviour)
    - 저작 데이터로 `entityId`를 가진다.
    - `BindTo(registry)`로 바인딩한다. 이미 바인딩되어 있으면 아무것도 하지 않는다.
    - 바인딩이 거부되면 Error 로그를 남기고 바인딩되지 않은 상태로 남는다.
    - `OnDestroy`에서는 자기 token으로 Unbind만 한다. 사망 처리를 하지 않는다.
  - `SceneEntityBinder`(IDisposable)
    - 생성할 때 이미 로드된 씬을 바인딩하고, 그 뒤 `sceneLoaded`마다 그 씬의 `EntityView`를 바인딩한다. 비활성 객체도 포함한다.
    - 씬 계층을 순회할 뿐이며, 서비스를 조회하지 않는다.
- **Bootstrap**
  - `CompositionRoot`가 `EntityPresentationRegistry`를 만든다.
  - `StartSceneBindings()`가 binder를 만들어 Application scope에 등록한다.
  - `GameBootstrapper.Awake`가 `StartSceneBindings()`를 호출한다. EditMode에서 root만 만드는 테스트는 열린 씬을 건드리지 않는다.
- **테스트 방 ID:** 플레이어는 `900001`, 테이블은 `900101`이다. 900000번대는 생성된 테스트 씬 전용으로 두고, 콘텐츠 ID가 아니다. 범위는 M2에서 다시 정한다.
- **관련 수정 (ADR-572 보완)**
  - `FirstPersonPlayerRig`는 입력 에셋을 `Instantiate`한 복사본을 쓰고, rig가 파괴될 때 그 복사본도 파괴한다.
  - 공유 에셋을 직접 켜면 그 에셋에 입력 상태가 남는다. 실제로 rig가 켜진 테스트 방을 연 뒤에 `InputTestFixture` 테스트를 실행하면 Input System 오류("Cached unprocessed value ... outdated")로 6개가 실패했다.
  - Domain Reload를 끈 Editor에서 Play를 반복할 때도 같은 잔존이 생길 수 있다.

## Alternatives
- **문자열 ID:** 채택하지 않았다. 범위 정책(ADR-018)이 숫자 범위를 암시하고, 저장·비교 비용이 작은 쪽을 택했다. M2에서 바꿀 수 있도록 struct로 감쌌다.
- **중복이 오면 나중 것으로 교체:** 채택하지 않았다. 16-17은 중복 권한을 금지하며, 교체하면 이전 객체의 콜백이 새 바인딩을 해제하는 경로가 생긴다.
- **`EntityView`가 `Awake`/`OnEnable`에서 스스로 등록:** 채택하지 않았다. 등록부를 찾으려면 정적 조회가 필요해 Manual DI 규칙(ADR-569)에 어긋난다.
- **registry를 UnityAdapters에 두기:** 채택하지 않았다. 순수 C#이면 Application에 둘 수 있고, headless와 EditMode에서 그대로 검증할 수 있다.

## Consequences
- **씬을 따로 열었을 때:** 테스트 방만 열고 Play하면 Bootstrap이 없으므로 바인딩도 일어나지 않는다. Bootstrap 씬에서 시작하면 바인딩된다. 4단계(줍기·놓기)에서 바인딩이 필요해지므로, 미결정 "Bootstrap 자동 로드"를 그때 함께 정한다.
- **아직 바인딩을 쓰는 곳이 없음:** 물리·상호작용 콜백이 token을 들고 오는 경로는 4~5단계에서 붙인다. 그래서 UNITY_T023은 token 수준까지만 검증했다.
- **Scene scope:** 아직 쓰지 않는다. 씬별 바인딩 정리는 `EntityView.OnDestroy`에 맡긴다.

## ValidationEvidence
- 2026-11-26 원래 프로젝트의 Editor가 열려 있어 scratchpad 사본에서 실행했다. `.meta` 15개는 사본에서 Unity가 만든 것을 옮겼고, 테스트 방 씬은 사본에서 다시 생성했다.
- **headless:** `dotnet build`·`dotnet test` 2/2 Passed. 새 Domain·Application 코드가 Unity 없이 경고 0으로 컴파일된다.
- **EditMode 34/34 Passed:** 등록부 테스트 8개 추가. UNITY_T024 포함.
- **PlayMode:** 28개 중 26 Passed, 2 Skipped(Input System 패키지 자체 테스트의 Ignore). exit 0, 컴파일 경고·오류 0건.
  - 테스트 방의 `EntityView` 2개가 각자 자기 ID로 바인딩되고, 역조회하면 같은 GameObject가 나온다.
  - UNITY_T024: 복제본은 거부되고 원본은 유지된다. 복제본을 파괴해도 원본 바인딩은 남는다.
  - `EntityView`를 파괴하면 그 Entity만 해제된다.
  - UNITY_T023: 씬을 다시 로드하면 이전 token은 current가 아니며, 그 token으로 Unbind해도 새 바인딩이 해제되지 않는다. 새 generation은 이전 값보다 크다.
  - Bootstrap 씬을 거쳐 테스트 방을 열면 `CompositionRoot`의 등록부에 바인딩된다.
- **음성 확인** (사본의 등록부만 바꾼 뒤 되돌림): 중복을 덮어쓰고 generation을 무시하도록 바꾸자 다음 테스트가 Failed였다.
  - EditMode: UNITY_T024, 이전 token 해제 테스트
  - PlayMode: UNITY_T024, UNITY_T023
- 테스트 실행 뒤 사본과 원래 프로젝트의 `Assets/`, `ProjectSettings/`, `Packages/`가 같았다.
- 원래 프로젝트의 Editor에서는 아직 이 코드를 컴파일하지 않았다.
