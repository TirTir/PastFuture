# ADR-572 M1 1인칭 이동·카메라·입력과 테스트 방

- Status: Validated (자동 테스트 범위. 조작감은 사람이 Editor에서 직접 플레이해 봐야 해서 아직 확인하지 않았다)
- SourceStep: 17 / M1 2단계 (2026-11-26, 사용자 승인 "2단계 진행")
- Related: ADR-499(제목만), ADR-565, ADR-569 / Handover 4절 M1, 16-3, 16-8, 16-17

## Context
- **M1 범위 (Handover 4절):** 방/복도, 카메라, 이동/충돌, 입력. 완료 기준에 "조작 자연스러움"이 들어 있다.
- **16-8 (원문 미확보, 재구성):**
  - 이동은 `CharacterController`가 초기 후보다.
  - 카메라 방향, 마우스 감도, 입력 버퍼는 표현 계층에 속한다.
  - 지속 이동은 입력을 병합해 처리하고, 줍기·대화 같은 단발 행동은 개별 Command로 처리한다.
  - InputMap 후보는 Gameplay/Interaction/Ability/Vehicle/Smartphone/Investigation/UI/Cinematic/Debug다.
- **16-17:**
  - Player Rig 후보는 CharacterController/PlayerMotor/Input/InteractionProbe/AbilityTargeting/CameraPivot/Hands/AudioListener다.
  - 생명주기는 Update에서 입력, FixedUpdate에서 물리, LateUpdate에서 카메라를 다룬다.
  - 20배 시간을 `timeScale`로 구현하지 않는다.
- **원문 한계:**
  - ADR-499(CharacterController 기반 초기 1인칭 이동)는 제목만 남아 있다.
  - 이동 속도, 점프·앉기 여부, 조작 키는 원문과 GDD에 없다.
- **템플릿 입력 에셋:** 템플릿의 `Assets/InputSystem_Actions.inputactions`는 ADR-567에서 "M1에서 교체 검토"로 보류한 파일이다. 지금도 project-wide actions로 등록되어 있다.

## Decision
- **계층**
  - `PastFuture.UnityAdapters.Player`
    - `PlayerMotor`: `CharacterController` 어댑터. 게임 규칙과 WorldState는 다루지 않는다.
    - `PlayerMotorMath`: 속도 계산만 하는 순수 함수.
    - `MovementSettings`: 이동 설정값.
  - `PastFuture.Presentation.Player`
    - `FirstPersonPlayerRig`: 입력을 읽고 카메라를 돌린다.
    - `FirstPersonLookState`: yaw/pitch 계산만 하는 순수 상태.
    - `LookSettings`: 시점 설정값.
  - asmdef 참조 변경
    - Presentation에 `Unity.InputSystem`을 추가했다.
    - Editor에 `PastFuture.UnityAdapters`, `PastFuture.Presentation`, `Unity.InputSystem`을 추가했다.
    - PlayMode 테스트에 `PastFuture.UnityAdapters`, `PastFuture.Presentation`을 추가했다.
    - 추가한 참조는 모두 기존 허용 범위 안이라 `AllowedProjectReferences`는 바꾸지 않았다.
- **입력:** `Assets/PastFuture/Settings/Input/PastFutureControls.inputactions`를 새로 만들었다.
  - `Gameplay` 맵
    - Move: WASD, 2D 벡터
    - Look: 마우스 delta
    - Sprint: 왼쪽 Shift
  - `UI` 맵
    - ReleaseCursor: Esc
    - CaptureCursor: 마우스 왼쪽 버튼
  - Keyboard&Mouse만 지원한다.
  - 템플릿 `InputSystem_Actions`는 삭제하지 않았고 project-wide 등록도 바꾸지 않았다. 처리 방법은 미결정이다.
  - Rig는 serialized 필드로 이 에셋을 참조한다. C# 래퍼 클래스는 생성하지 않는다.
  - 2026-11-26 보완 (ADR-573): rig는 에셋을 `Instantiate`한 복사본을 켜서 쓰고, rig가 파괴될 때 복사본도 파괴한다. 공유 에셋에 입력 상태가 남지 않게 하기 위해서다.
- **이동**
  - Update에서 실제 `Time.deltaTime`으로 `CharacterController.Move`를 호출한다. 게임 시계와는 독립적이다.
  - 평면 속도는 `MoveTowards`로 가속·감속한다.
  - 대각선 입력은 길이를 1로 제한해 직선보다 빠르지 않다.
  - 벽에 밀어붙여도 속도가 쌓이지 않도록, 실제로 이동한 속도(`controller.velocity`)만 남긴다.
  - 땅에 있을 때는 작은 하강 속도를 유지해 경사와 계단에 붙어 있게 한다.
- **잠정 수치:** 아래 값은 M1 6단계 시간 배율 측정 후 다시 정한다.
  - 걷기 3.0m/s, 달리기 5.5m/s
  - 가속 20m/s², 감속 25m/s², 중력 9.81m/s²
  - 높이 1.8m, 반지름 0.3m, stepOffset 0.3m
  - 카메라 높이 1.6m, FOV 70°, pitch ±85°, 감도 0.1°/px
- **`CharacterController.minMoveDistance = 0`:** `PlayerMotor.Awake`에서 강제한다.
  - 기본값 0.001m에서는 프레임 시간이 짧을 때 한 프레임 이동량이 그보다 작아 이동이 통째로 무시된다.
  - 실제로 batchmode(프레임당 약 0.0001초)에서 플레이어가 전혀 움직이지 않았다.
- **점프·앉기·게임패드·리바인딩·head bob:** 원문에 근거가 없어 넣지 않았다.
- **Rig의 실행 순서:** `DefaultExecutionOrder(-100)`로 `PlayerMotor`보다 먼저 입력을 읽는다. yaw는 몸체에, pitch는 `CameraPivot`에 LateUpdate에서 적용한다.
- **입력 활성 상태 (2026-11-26 수정):** 이동·시점·달리기 입력을 받을지는 rig가 가진 `IsInputCaptured` 값으로 정한다.
  - 활성화할 때 켜고, Esc로 끄고, 마우스 왼쪽 버튼으로 다시 켠다. 앱 포커스를 잃으면 끈다.
  - 커서 잠금(`Cursor.lockState`)은 화면 표현으로만 맞춘다.
  - 처음에는 `Cursor.lockState`를 읽어 판단했다. 그런데 창이 없거나(batchmode) Editor의 Game 화면에 아직 포커스가 없으면 OS 잠금이 적용되지 않아, 입력이 모두 무시되었다.
- **의존성 규칙 해석 (ADR-569 Manual DI)**
  - 같은 rig 안의 컴포넌트와 설정 에셋을 serialized 필드로 연결하는 것은 서비스 조회로 보지 않는다.
  - 서비스(수명 있는 객체)는 계속 `Initialize(...)`로만 받는다. Rig는 아직 서비스를 쓰지 않는다.
- **테스트 방:** `Assets/PastFuture/Scenes/Test/M1_TestRoom.unity`
  - 생성기 `PastFuture.Editor.Dev.M1TestSceneBuilder.Build`가 만든다(메뉴 PastFuture/Dev/Generate M1 Test Room Scene). 다시 생성하면 덮어쓰므로, 배치는 손으로 고치지 않고 생성기에서 고친다.
  - 6×6m 방, 1.0×2.1m 문, 폭 2m·길이 10m 복도로 이루어져 있다.
  - 0.2m 낮은 턱(넘을 수 있음), 0.5m 블록(막힘), 테이블을 두었다.
  - 천장은 없고 Directional Light 하나다.
  - Build 씬 목록에 넣지 않는다. Bootstrap 없이 이 씬만 열고 Play해도 동작한다.

## Alternatives
- **템플릿 `InputSystem_Actions` 그대로 사용:** 채택하지 않았다. 맵 이름(Player)과 액션(Attack, Jump 등)이 16-8 후보와 다르고, Touch/XR 등 대상이 아닌 장치가 들어 있다.
- **Rigidbody 이동:** 채택하지 않았다. 16-8과 16-17의 초기 후보가 `CharacterController`이고, Rigidbody는 차량 같은 별도 어댑터용이다.
- **FixedUpdate에서 이동:** 채택하지 않았다. `CharacterController`는 물리 스텝과 독립적으로 Move하며, 16-17은 Update에서 입력을 처리한다고 정한다. 물리 상호작용 결과를 제출하는 것은 5단계에서 다룬다.
- **씬을 손으로 작성:** 채택하지 않았다. 생성기를 쓰면 배치를 재현할 수 있고, 테스트의 좌표 가정과 한 곳에서 맞출 수 있다.

## Consequences
- **Editor에서 플레이:** M1_TestRoom 씬을 열고 Play한 뒤 Game 화면을 클릭하면 WASD/마우스/Shift로 움직일 수 있다. 사람이 해 보는 조작감 확인은 NotRun이다.
- **테스트 방식:**
  - 이동·충돌 테스트는 입력 rig를 끄고 `PlayerMotor`를 직접 움직인다.
  - 키보드·마우스에서 rig, motor까지의 연결은 `FirstPersonRigInputTests`가 검사한다. Input System의 `InputTestFixture`로 가상 키보드와 마우스를 만들어 쓴다.
  - 이를 위해 `Packages/manifest.json`에 `"testables": ["com.unity.inputsystem"]`을 추가했고, PlayMode 테스트 asmdef가 `Unity.InputSystem`과 `Unity.InputSystem.TestFramework`를 참조한다.
  - 그 결과 PlayMode 실행에 Input System 패키지 자체 테스트 4개가 함께 포함된다. 이 중 2개는 패키지가 스스로 Ignore로 표시한다.
- **커서 잠금 시점:** Play를 시작하면 바로 입력이 켜진다. 그래서 Editor에서 마우스가 Game 화면 밖에 있다가 들어오면, 그 움직임이 시점 회전으로 들어갈 수 있다. 바꿀지는 조작감 확인 때 정한다.
- **이동이 쓰는 시간:** 이동은 실제 시간 기준이다. 게임 시간 20배 환산은 6단계에서 측정한다.
- **Bootstrap과의 관계:** Bootstrap 씬에서 테스트 방을 불러오는 흐름은 아직 없다. 미결정 "Bootstrap 자동 로드"와 함께 정한다.
